# Exploratory reads by default, with mandatory disclosure

TCKDB serves `/api/v1/scientific/*` under an explicit read profile. `exploratory` — every visible candidate, with its review state, carrying no TCKDB recommendation — is the **default**; `curated` — records at or above the `approved` review floor, reported alongside the dataset release backing them — is opt-in via `?profile=curated`. The miscitation risk this creates is answered by disclosure rather than by narrowing: the resolved profile and a separate `profile_recommendation` token are echoed in every scientific response and in every dataset manifest, and `exploratory` states in machine-readable form that TCKDB endorses nothing. The two tokens are deliberately not redundant, and the disclosure only works if it is *true*: `curated` on the general read surface reports `approved_floor_only` — a human reviewer accepted these records, which is not the same as TCKDB recommending them over their siblings. The stronger `tckdb_curated_release` is emitted only by `/scientific/releases/*`, where every record served was resolved through an attributed selection. An earlier version emitted it for any curated read once any release existed, because the backing release was resolved per *database* rather than per record; that claimed an endorsement for records no curator had ever looked at, including candidates a curator had explicitly passed over, and it turned the mitigation into the misinformation it was meant to prevent.

The default is a product call, not an oversight, and it is expected to flip. Every record on the deployed corpus is currently `under_review`. A curated default would return empty result sets from every endpoint, which a new user cannot distinguish from a broken database, and which would be read as "TCKDB has no data" rather than "TCKDB has not yet curated its data". The failure mode of the chosen default is a user citing a candidate as though it were a recommendation; the failure mode of the alternative is a user concluding the project is empty and leaving. The first is mitigable by disclosure and the second is not, so the first is the one we take. Recording it here means the reversal, once a curated corpus exists, is a deliberate decision rather than an accident.

The mechanism is chosen to make partial adoption impossible. The profile is resolved once, in an `async` router-level dependency attached to the whole scientific router, so every operation — including the POST searches — declares `profile` and `release` in the published OpenAPI, and the resolved value reaches the service layer through a context variable rather than through seventy route signatures and forty service entry points. Threading it manually would have guaranteed that some endpoint eventually forgot it, and *a profile that only some endpoints honour is worse than none, because it teaches consumers to trust it*. Behaviourally the profile is applied at two seams that between them cover the whole surface: `visible_statuses`, which every search and subresource read already calls, and `resolve_path_handle`, which every detail-by-ref read resolves through — roughly half the read services never call the former, and without the latter `profile=curated` returned never-reviewed records under a curated echo. In both, `curated` raises the floor to `approved` and overrides the `include_rejected` / `include_deprecated` opt-ins, because "show me what TCKDB stands behind, and also the rejected records" is not a coherent request. The handle floor deliberately applies only to handles naming a record the endpoint *returns*, never to scoping parents: gating `species_entry` would hide an approved thermo behind an identity row that merely had not been reviewed, which on a corpus where everything starts `under_review` would 404 the entire curated surface. The floor only ever narrows: a caller passing a stricter threshold keeps it, and outside a scientific HTTP request the profile is `exploratory`, so nothing that existed before this change behaves differently.

The dependency is `async` for a non-obvious reason worth recording. FastAPI runs synchronous endpoints in a worker thread whose context is *copied* from the request task, so a context variable set in an async dependency is visible to the endpoint and everything it calls, whereas one set inside a synchronous dependency would be set in a different, discarded copy and would silently do nothing. The two surfaces that cannot carry a JSON envelope are handled explicitly rather than skipped: the streaming exports capture the profile eagerly and report it in their manifest line, because a generator can outlive the request-scoped context, and the one binary endpoint reports `X-TCKDB-Read-Profile` as a response header.
