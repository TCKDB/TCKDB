# Custody of stored evidence is recorded, not logged

TCKDB refuses a reaction whose atoms do not balance, refuses a saddle point made of the wrong elements, and refuses an atom map that contradicts its own IRC. Those refusals are positions about chemistry, enumerated in `docs/guides/scientific_check_register.md`. This decision states the position that was missing: what TCKDB does when its *own* object store hands back bytes that are not the bytes it stored. Until now the answer was a 502 and a traceback in the journal, which is to say the database applied a standard to its contributors that it did not apply to itself.

A SHA-256 mismatch on retrieval is not a transient error and it is not an HTTP incident. The store is content-addressed: the key *is* the digest, so a body that does not hash to its key is either corruption of a stored artifact or a swapped object, and neither retries away. Treating it as a 5xx means the failure lives exactly as long as the request. The next reader of that artifact gets another 502; a reader of the *record* — the calculation, the thermo derived from it, the release that cites it — is told nothing at all, because nothing about the record changed. **A log line nobody greps is not a record.** The rule this decision adopts is that a break in custody of stored evidence produces a durable row, and that row has a read-time consequence.

## The record is keyed on the object, not on the row

The durable form is `artifact_integrity_event`: append-only, one row per observation, keyed on `sha256` with a nullable `artifact_id`. Keying on the digest rather than on the artifact row is the substantive choice. In a content-addressed store the unit of corruption is the *object*, and one object is routinely shared by many `calculation_artifact` rows across unrelated calculations — that sharing is the point of content-addressing. A per-row foreign key would let a corrupt object condemn the one record whose download happened to discover it while its N-1 twins went on reading as sound, which is the same "found only if someone stumbles on it" failure in a new place. The digest key also makes the `store_artifact` dedup path recordable at all: there, verification fails against an object whose referencing row does not exist yet, because the upload that would have created it is being refused.

## Three causes, three remedies, and the columns that separate them

A digest mismatch has three distinct causes: the store returned wrong bytes on this read, the object was modified after it was written, or the digest was computed wrongly at ingest and TCKDB never stored what it said it did. They call for entirely different responses — retry and re-verify, audit who holds write credentials on the bucket, or audit the ingest path — and an operator who cannot tell them apart will investigate the wrong one. The row therefore captures, at the moment of detection, both what was expected and what was found, plus the store's own metadata for the object (`LastModified`, `ETag`, `ContentLength`, from a cheap `HEAD`). Comparing `object_last_modified_at` against `artifact_recorded_at` separates "modified after write" from "never stored correctly"; comparing `object_etag` and `object_content_length` against the bytes actually read separates both of those from a faulty retrieval, where the object may still be sound. `artifact_recorded_at` is a *copy* of the artifact row's `created_at` rather than a join, because the comparison must not depend on a correspondence this table exists precisely to doubt.

Nothing is repaired, quarantined or deleted on detection. A corrupt object is the only surviving evidence of whatever happened to it, and an automatic response that destroys it converts a diagnosable incident into a permanent mystery. Remediation is an operator decision taken against the record.

A record that stays condemned after its evidence is restored would be a trap rather than a judgement, so the table is an append-only log of *observations* rather than of breaks alone: an object that reads back correctly is recorded as a later `verified` observation, and the trust evaluator reads the latest observation per digest. The break is never edited or deleted — it remains the account of what happened. A check constraint requires a `verified` row to carry `observed_sha256 = sha256`, so a hard fail can only be cleared by bytes that actually hash correctly, never by an operator asserting that they do. Clean reads are recorded only for digests that already carry a break; writing a row per successful read would turn an incident log into a download log and make the trust query proportional to traffic.

## Detection changes trust, and `artifacts_present` still does not verify

This decision changes trust semantics and says so rather than doing it quietly. A recorded break promotes the owning calculation to `HardFailReason.artifact_integrity_failed`, which propagates to every product that names that calculation as a required source through the existing `source_calculation_hard_failed_for_required_role`. Before this, a record whose evidence had provably rotted graded normally. It is a hard fail because the alternative is to keep publishing an evidence-completeness score computed over bytes TCKDB cannot produce. Note what it is *not*: every other hard-fail reason says the record is internally wrong, and this one says the record may be perfectly correct and we can no longer show you what it rests on. Those are different claims and the reason is documented as such.

The trust rubric's `artifacts_present` check keeps its existing meaning and deliberately does **not** verify bytes. It asserts a claim about the *depositor* — this calculation retained its evidence — which a row satisfies. Byte integrity is a claim about *TCKDB*. Fusing them would break two things at once. First, rubric runners are pure and I/O-free by contract, which is what makes an evaluation deterministic; a check that fetched from object storage would make a trust grade a function of the network, so the same record would score differently on two consecutive reads. Second, and worse, a storage outage would become indistinguishable from a contributor who never uploaded a log, and the corpus-level statistic "how many calculations retained their logs" would silently track object-store health. This is [0002](0002-separate-reproducibility-from-trust.md)'s separation of independent judgements applied to a third axis, and the boundary matters more than the convenience of one fewer place to look.

The consequence is that the hard fail asserts only what has actually been *detected*. Absence of the reason is not a verification claim, and must never be read as one: an artifact nobody has downloaded has been checked by nothing.

## Verification is triggered by a citable claim, not by a clock

That gap — coverage proportional to download traffic rather than to importance — is real, and the honest fix is a verification pass. `backend/scripts/ops/verify_artifact_integrity.py` re-reads stored objects and records what it finds.

It is deliberately **not** a cron job. A blanket periodic sweep re-reads every byte on a schedule chosen for no scientific reason; its cost scales with total stored volume while its value scales with what someone will actually cite, and on S3 it manufactures egress charges forever. The trigger this decision adopts instead is **cutting a dataset release** (`backend/docs/deployment/cutting_a_dataset_release.md`). A release is the exact moment TCKDB turns a set of records into a citable claim, so it is the moment "we still hold the evidence behind these" has to be true, and the scope is bounded by the release rather than by the bucket. Two more triggers were already present and merely silent, and are now wired to record what they see: archive export streams every object through `load_artifact_bytes` with its expected size (`backend/app/services/archive/core.py:321`) — it has been a full verification pass all along — and the ESS-parameter backfill reads every stored input log (`backend/app/services/calculation_parameter_extraction.py:366`), where an integrity failure previously escaped an except clause that promised to skip on any failure, and stopped the backfill at the first corrupt object. Operators who want continuous coverage between releases should sample (`--sample`), which buys a detection-time distribution rather than a guarantee, and is the right shape for a background cost.

Orphan detection — content-addressed objects no longer referenced by any row, accumulated by rolled-back uploads (`backend/app/services/artifact_persistence.py:253`) — is nearly free alongside a sweep that is already enumerating the bucket, and the sweep reports it. It stays a *report*, never a delete: the compensation path retains objects precisely because a digest may be shared by a committed row or a concurrent transaction, and a garbage collector that cannot see concurrent writers is a data-loss mechanism wearing a maintenance hat.

## Amendment (2026-08-10, integrity-cluster follow-ups)

**One owner, and the rubric cites it.** The reproducibility rubric has re-read graded output logs through `load_artifact_bytes` since before this decision, and on a mismatch it recorded a warning in its own snapshot and nothing durable. Two tiers therefore held the same fact with different consequences, which is exactly what [0008](0008-validation-tiers-definitions-block-expectations-warn.md) forbids: the reproducibility snapshot could say an artifact had failed integrity while the trust layer graded the calculation normally, and which answer a reader got depended on which path ran last. The custody record owns the fact. The rubric now writes its detections here — under a new `reproducibility_verification` detection context, so the coverage column stays honest about which population of objects a rubric re-read actually covers — and, for artifacts it does not read itself, copies the recorded verdict and cites the observation id it copied. A clean rubric read of a digest carrying a break appends a `verified` observation, the same way the sweep clears one.

**`--release` was sweeping nothing.** The scope query filtered `release_selection.record_type = 'calculation'`, a value the `selectable_record_type` check constraint forbids. The release gate — the trigger this decision chose over a cron — therefore matched zero digests and exited 0. It now walks the standing selections, the calculations each cites through its `*_source_calculation` table, and the transitive `calculation_dependency` closure above those, which is the evidence a reader following a release's provenance actually reaches.

**Orphans are reclaimable in two steps, and the race that remains costs a key rather than bytes.** This decision left unreferenced objects as a report on the grounds that a collector which cannot see concurrent writers is a data-loss mechanism. That reasoning is intact and is why the reclaim is split rather than why it stays undone. The first step *moves* an object that has been unreferenced for at least `--orphan-age-days` (default 30, floor 7) to a `reclaimed/` hold, re-reading the reference set in a fresh session immediately beforehand. The second, `--purge-hold-days` (floor 7), deletes from the hold.

**The move can still lose a race, and the honest statement of what is guaranteed is narrower than "nothing can begin referencing it".** `store_artifact` deduplicates: an upload of bytes already at the content-addressed key HEADs, verifies, and returns *without writing*, with its database transaction still open. So a genuine 31-day-old orphan can be deduplicated against mid-sweep, moved to the hold while that transaction is uncommitted, and then acquire a committed `calculation_artifact` row pointing at a digest whose object is no longer at its key. The window is seconds wide and requires a dedup hit against a month-old orphan inside it. What is actually guaranteed is this: **the bytes survive it** — the object is in the hold, `--purge-hold-days` re-reads references and refuses to delete a held digest any row points at, and `--restore <sha256>` puts it back. The observable cost of losing the race is a spurious `object_missing` finding and a hard fail on a legitimate new calculation until an operator restores it. That is a real cost and it is written here rather than in a commit message.

What the design *does* guarantee, and what makes the hold coherent rather than merely a delay: a held object is not at its content-addressed key, so a later upload of the same bytes takes the `HEAD` → 404 → `put_object` path and repopulates the key byte-identically. Content addressing makes divergence impossible — there is no state in which the key holds bytes that differ from the held copy — so a restore can never resurrect a stale version, and a re-upload can never silently shadow one. `--restore` therefore refuses an occupied key rather than overwriting it: the copy already there is what every row is reading, and overwriting would be either a no-op or the destruction of a genuine corruption this record exists to preserve.

Both age gates are floors enforced in the parser, not defaults. `--orphan-age-days 0` would reclaim uploads still in flight and `--purge-hold-days 0` would empty the hold before anyone could notice a mistake, and a guard that any invocation may set to zero is not a guard. An object the store will not date is treated as unknown age and left alone rather than assumed ancient.

**The record is readable, aggregated at read time and never at rest.** The consequence of a break reached clients while the evidence for it did not, so a curator could be told a record was untrustworthy and had no way to find out what happened to it. `GET /scientific/artifacts/integrity` answers that, one record per digest — first seen, last seen, how many, which reads have looked, the latest verdict, expected against observed — with the full sequence at `/{sha256}/integrity`. Aggregating on the list is the answer to unbounded repeat detections: appending a row per read is deliberate, because a break that recurs across months is a different story from one that happened once, but a listing of raw observations would bury one incident under its own retries. Nothing is collapsed in the table; the aggregation is a projection, the log stays append-only, and the history endpoint returns observations oldest-first because "broken, then verified, then broken again" is a claim about the storage layer that no current-state summary can express. Curator or admin, not the public read surface: the rows carry verifier prose and the object store's own `ETag`, which is operational detail about a deployment rather than science about a record — the same reasoning that gates raw bytes in [0004](0004-store-artifacts-verbatim-gate-raw-log-access.md).
