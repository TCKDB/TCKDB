# Curated selections are a release overlay, not a column

A curator's answer to "what is *the* TCKDB value?" is recorded in `release_selection`, an append-only curation table naming the policy version, the curator, the chosen candidate, the subject it is chosen *for*, a mandatory rationale, and the dataset release it belongs to. It addresses the science with the same loose `(record_type, record_id)` pointer that `record_review` and `scientific_record_supersession` already use, and writes nothing to `thermo`, `statmech`, `transport`, `kinetics`, `network_solve`, or `transition_state_entry`. No product table gains an `is_best`, `is_preferred`, or `selected_release_id` column, and a test asserts that appending a selection leaves the selected row byte-identical.

The alternative sketched in the original candidacy spec — a `species_product_selection` table keyed on `(species_entry_id, product_type, product_id, selection_kind)` with mutable rows — was rejected. It would have reintroduced preferred/selected semantics as editable state, one row per subject, silently rewritten each time someone changed their mind. Scoping the selection to a **named, versioned dataset release** instead turns the claim from a moving one into a fixed one: "the TCKDB value" becomes "the TCKDB value *as of release 2026.07.0*", which is what a citation actually needs to mean. It also makes the honest answer expressible — a `withdraw` row says the release recommends nothing for that subject, which is a legitimate curatorial position and strictly better than leaving a stale recommendation in place.

Revising a decision appends. A curator inserting a `supersede` row names the row it replaces; the earlier rationale, curator, and timestamp survive verbatim, and the published `selection_ledger.ndjson` shows the whole chain. This is enforced three ways — no `UPDATE`/`DELETE` in application code, a database trigger that rejects both so direct SQL clients are bound by it too, and a `UNIQUE` constraint on `supersedes_selection_id` that keeps chains linear. There is deliberately no `is_current` column; "which selection stands" is computed as head-of-chain-and-not-withdrawn, because a mutable flag would be a second source of truth able to disagree with the ledger it summarises. This mirrors the reasoning in ADR 0003 for accepted science and ADR 0002 for reproducibility: a claim about a record is stored beside the record, never inside it.

A published release freezes an immutable, checksummed manifest, and ships its selections **together with every candidate they were chosen from and the review history behind them**. A release that shipped only the winners would be precisely the "trust us" artifact this layer exists to replace — disagreeing with a TCKDB recommendation must require no privileged access. Every shipped line carries chemical identity and level-of-theory/software provenance, because a deposited file that states a heat of formation against an opaque handle is not checkable offline and ships less science than the unauthenticated read API.

Publication is the only write: the manifest document, each artifact's bytes, and a snapshot of every claim the release makes are stored at that instant and served unchanged forever. Re-deriving them on read was tried and is wrong. It meant one ordinary upload for a released species changed the candidate set and made the citation stop resolving — on a corpus where review is *expected* to progress, the citable window was effectively zero — and it meant recording the DOI, the final step of publishing, permanently broke the digest, so `verified: true` was reachable only for releases nobody had deposited. Both are normal events; a release is a snapshot claim, and new science arriving afterwards is the system working. Whether the live database still agrees is a real question, reported separately and non-fatally as `live_divergence`, and it never blocks a download. Selections are additionally restricted to `approved` records, because the accepted-science immutability trigger only freezes a product row once approved — without that restriction a release could recommend a value that is still editable after publication. This is a fourth contract alongside the three separated in ADR 0001: `tckdb.dataset_release.v1` is citable, immutable, curated, and explicitly **not** re-ingestible, where `tckdb.archive.v1` is a lossless operator backup that is explicitly **not** citable, and `tckdb.export.v0` is a convenience projection that claims neither. Each states the distinction inside its own manifest so a consumer holding only one of them cannot confuse it for another.

Finally, TCKDB does not mint DOIs. `dataset_release.doi` is nullable, stays `NULL` until a deposit has actually been made, and is refused if it would repoint an existing one. A DOI is not retractable, and minting one to satisfy a checklist before the corpus is publishable would be an irreversible mistake; the deposit is a documented manual step performed when a paper tag is cut.
