# Hold literature-reported pressure-dependent kinetics

A set of phenomenological k(T,P) may be attached to a network either because the master equation was solved in this database or because the values were transcribed from a publication, and `network_solve.kind` says which. The `computed` member is the default and the preferred form, and every coverage rule that applied before this decision still applies to it unchanged. The `reported` member is not held to the state-energy, channel-barrier or energy-transfer coverage rules, requires `literature_id` instead, and raises the `reported_network_solve` upload warning. This is as much a correction as an accommodation: `network_solve` has always called itself a master-equation solution while requiring no column that evidences one, and `kind` is the first thing in the record to make that claim explicit and checkable.

Until now published k(T,P) could not be deposited at all. The chain was structural rather than deliberate: `network_kinetics.solve_id` is NOT NULL, `channel_kinetics` is reachable only through a solve, and a solve triggers three coverage rules — exactly one energy per network state, exactly one barrier per saddle-point path, and a collisional energy-transfer model for every well. Each of those rules is right for a solve run here; each asks for something that a paper's supplementary table, by construction, does not contain. A depositor holding a PLOG or Chebyshev fit out of a combustion-kinetics paper — the ordinary currency of the field, and the form in which most pressure-dependent kinetics actually reach a mechanism — was refused outright. The refusal produced no better data, only less: the numbers went into somebody's private mechanism file instead, uncited and unversioned. This is the argument [0005](0005-record-environments-do-not-grade-them.md) made for accepting a `described` execution environment and [0009](0009-record-what-energy-transfer-was-specified-over.md) made for accepting a network-wide ⟨ΔE⟩down — a validation rule that can only be satisfied by data the depositor does not have does not improve the record, it deletes it.

The obvious alternative was to relax `network_kinetics.solve_id` to nullable and hang reported rates off the channel directly. It is the wrong shape for two reasons. It would duplicate the solve's literature / software / workflow-tool provenance triple onto `network_kinetics`, where it would immediately be free to disagree with the copy on the solve. More seriously, a NULL `solve_id` would carry two incompatible readings — "these rates were transcribed from a publication" and "the writer never linked the solve" — with nothing in the row to separate them. That is precisely the ambiguity [0009](0009-record-what-energy-transfer-was-specified-over.md) removed for energy-transfer scope and that `network_channel.mechanism` removed for channel attribution, reintroduced one table to the left. A scientific claim about a record is positively asserted, never inferred from an absence. `network_solve` already carries the provenance triple, including the nullable `literature_id` a reported deposit needs, so the token belongs there and no new nullable FK appears. A check constraint then makes `literature_id` mandatory for the `reported` member, so the relaxation is paid for at the database level rather than only at the API boundary.

Calling such a row a "solve" when nothing was solved is a stretch, and it deserves an answer rather than a gloss. The answer is that the table has been over-claiming since it was created. `network_solve` was documented as "One master-equation solution for a reaction network" — a docstring this decision corrects — and *every column that would evidence a master-equation run is nullable*: `me_method`, `interpolation_model`, `grain_size_cm_inv`, `grain_count`, `emax_kj_mol`, and the whole `tmin_k`/`tmax_k`/`pmin_bar`/`pmax_bar` envelope. Before this decision not one *scientific* column on the table was NOT NULL — only the surrogate key, `network_id`, and the `created_at`/`public_ref` the mixins contribute — and `bath_gases`, `energy_transfers`, `state_energies` and `channel_barriers` are relationships that may all be empty. A row asserting "master-equation solution" purely by table membership, carrying no evidence that any master equation was ever run, has always been representable. What kept it from happening was a single Pydantic validator on a single write path — `NetworkSolveIn` plus `validate_mechanistic_channel_evidence` — and not the record itself. The unwired `NetworkSolveCreate` entity schema, on which every one of those fields is already optional, shows how cheaply a second write path would have produced one.

So the discriminator does not introduce an ambiguity into `network_solve`; it repairs one that was already there and merely undeclared. The honest reading of the table, and the one the ME settings have always been consistent with, is that it is the provenance envelope for one coherent set of k(T,P) — the T/P range they are valid over, the software and workflow tool that produced them, the paper they are credited to, and the channel rates that belong together — with the master-equation settings being what fills that envelope in when the numbers came from a run of ours. `reported` is not a new kind of thing smuggled into a solve table; it is an existing possible state of that table finally being named and made to declare itself. `kind` becomes the first NOT NULL column on `network_solve` that says anything scientific, which is the first time the table's central claim is stated in the record rather than assumed from its name. The claim is only half structural: the check constraint holds `reported ⇒ literature`, while `computed ⇒ master-equation inputs` still rests on `validate_mechanistic_channel_evidence` on the one wired write path — the same fragility identified above, now narrowed rather than eliminated. Making it structural would need a deferred constraint trigger, because a solve is inserted before the children that evidence it; that is worth doing and is not done here. It also converts an unqueryable gap into a queryable one: "which of my k(T,P) are backed by a master-equation run I can inspect?" was previously spread across nullable columns and empty relationships with no way to separate *not recorded* from *did not happen*, and is now one predicate. Renaming the table to match the envelope reading would churn public refs already minted on the deployed database (`nsolve_…`), the `/scientific/network-solves` route, and every client mirror, in exchange for a better noun; the token and the docstrings carry the meaning instead.

The axis is deliberately not `ScientificOriginKind`, which classifies how science was *produced*. A paper's k(T,P) is usually computed science — somebody solved a master equation for it. What `reported` records is not that the numbers are non-computational but that *this database does not hold their derivation*, which is a different question with a different answer.

Under [0008](0008-validation-tiers-definitions-block-expectations-warn.md) the tiers follow. Published k(T,P) is correct, common, citable science, so a check that refused it could fire on a correct result and must not block; the completeness limitation warns instead. What stays definitional still blocks: a `reported` solve with no literature would assert rates carrying neither a derivation nor a source, which is weaker than either form this decision meant to admit, and a `reported` solve with no `channel_kinetics` reports nothing and contradicts its own kind. Relaxed also means *not required*, never *unvalidated* — a reported solve that volunteers a bath-gas composition or a state energy is held to exactly the same referential and physical rules as a computed one. And nothing was loosened on the computed side: the two list fields that stopped being `min_length` constraints became conditions on the `computed` member, because a schema-level `min_length` cannot see the discriminator.

What a reader should conclude from a `reported` record is narrow and specific: these rate constants are what the cited publication printed, and this database holds no part of the calculation behind them. Three things are therefore impossible that a computed record permits — the rates cannot be re-derived, the fit cannot be checked against the underlying microcanonical data, and the network cannot be re-solved at temperatures or pressures outside the reported range. The values are as trustworthy as their source; what is missing is the derivation, not the accuracy. Two solves of the same network, one computed and one reported, are not equally informative, and the warning exists so that a consumer comparing them is told so rather than having to notice. For the same reason it surfaces on every read path that reaches a rate, not only on the solve itself: on the solve detail and search records, on the solve summary embedded in a network, on the parent-solve context of a network-kinetics record, and on the compact kinetics projection embedded in a network. A consumer pulling rates must be able to tell the two apart without a second request and a join, because a reported record that read back indistinguishably from a computed one would be worse than refusing the deposit it came from. `computed` remains the preferred deposit; this decision admits a weaker record, it does not declare the two equivalent.

## Amendment (2026-08-04, `f9b2e6c4a1d7`)

The asymmetry noted above — `reported ⇒ literature` structural, `computed ⇒ master-equation inputs` resting on `validate_mechanistic_channel_evidence` on the one wired write path — is now closed, by the deferred constraint trigger this decision said was worth doing and did not do. At COMMIT, a `network_solve` with `kind='computed'` must hold at least one `network_solve_state_energy`; at least one `network_solve_energy_transfer` if its network declares a `well`; and at least one `network_solve_channel_barrier` if its network declares a saddle-point path. It fires on insert and update of the solve, so relabelling a `reported` row cannot escape it, and on delete and update of the three evidence tables, so the evidence cannot be pulled out from under a committed claim; a whole-network teardown is unaffected, because by commit time there is no solve left to make the claim. A plain `CHECK` could not have done this: the solve is written before the children that carry its id, so a per-statement check would refuse every legitimate insert.

It is closed **to the extent of existence, not coverage**. The database now guarantees `reported ⇒ literature` and `computed ⇒ nonzero master-equation evidence of each applicable class`; the three coverage rules — one energy per state, one ⟨ΔE⟩down per (well, collider) pair or a `network_wide` declaration, one barrier per saddle-point path — remain properties of the wired upload path alone, and nobody should read the trigger as the whole contract. That boundary is where [0008](0008-validation-tiers-definitions-block-expectations-warn.md) puts it rather than where convenience did. A computed solve with *zero* state energies contradicts its own kind — it is exactly the over-claiming row this decision was written about, and a contradiction is definitional, so it may block. A computed solve with four energies out of five is an *incompleteness*, and an incomplete record is still a true one, to be graded by the trust and reproducibility layers rather than refused. Reimplementing coverage in PL/pgSQL would also put one rule in two languages with two consequences, free to disagree: [0009](0009-record-what-energy-transfer-was-specified-over.md) *relaxed* a coverage rule after the fact, and a full-coverage trigger written before it would have refused every legitimate network-wide deposit as an opaque commit-time error until a lockstep migration reached the deployed database. Existence is monotone under every such relaxation, so this trigger can never drift stricter than the validator — which is why each rule is gated on the topology, an all-barrierless network and a well-less one having legitimately zero rows of the relevant class. The residual gap is at least queryable, in the same sense this decision claimed for `kind` itself: three set-difference queries find any computed solve that passes existence and would fail coverage, where before there was no predicate at all.

The validator is untouched and is still the full contract. The trigger is belt and braces — the floor under write paths that never reach it, including the unwired `NetworkSolveCreate` this decision named as the cheap route to a false `computed` record.

## Amendment (2026-08-04, mechanism export)

The claim above that `kind` surfaces "on every read path that reaches a rate" holds for the JSON surfaces and cannot hold for CHEMKIN. A mechanism file has no field for provenance — only `!` comments — and comments are routinely stripped by the simulators such files are written for. So a `reported` solve's PLOG or Chebyshev block, once exported, would be indistinguishable from a rate this database derived, and would propagate into every simulation built on that file. That is the failure this decision names as worse than refusing the deposit, reached by a different door.

There is no live gap: `chemkin_serialize` reads only the classic `kinetics` table and network kinetics never reach mechanism output. The decision recorded here is therefore about the moment that changes, and it is deliberately *not* a choice of mechanism. Three answers are defensible — annotate the rate with a `!` comment carrying the origin, following the `! SMILES=… ref=…` idiom the file already uses per species; exclude `reported` solves from mechanism export unless explicitly asked for; or gate them behind an include token so requesting transcribed rates in a mechanism is a named, deliberate act. Which is right depends on how the export is consumed, and that is not knowable in advance of someone needing it.

What is *not* defensible is emitting them with no disclosure at all, which is what happens by default if nobody thinks about it — and nothing in the code forced anybody to think about it. `backend/tests/api/scientific/test_chemkin_reported_solve_disclosure.py` now does: it passes while the serializer touches no network kinetics, and fails the moment it does without also reading the solve's origin, with the three options in the failure message. It is a tripwire on a decision, not a test of behaviour that exists, and it says so.
